One false alarm worth recording, because I nearly logged it as a defect: I probed
the spinner with `s.querySelector('svg')` and got nothing, which looked like the
icon failed to render. It had rendered. Lucide **replaces** each `<i data-lucide>`
with an `<svg>` that keeps the `data-lucide` attribute and gains `class="lucide"`,
so the element I had selected *was* the SVG. The probe was wrong, not the app.

Another, this one about a real behavior: my first attempt to catch the loading
frame delayed `/books` and found a blank table. That was not a broken loading
state either. `tryAutoLogin` (`ui.js:244`) fires its **own** `/books` probe and only
calls `loadBooks()` once that resolves, so a delayed `/books` opens a window where
the table is legitimately still empty and the login card is up. That is the auth
handshake, not the list loading.

Nothing in this audit is now unverified. Two items remain blocked on you rather
than on tooling, and are listed at the end of this document: the SRI hash on the
Lucide CDN script, and the written reason for the single-icon-library choice.

## Defects found during remediation (not in audit 001)

Writing the fix, and then running it, surfaced eleven further problems, five of
them introduced by my own first pass. Listed because a fix pass that only claims
the original findings is hiding its own regressions.

| # | Defect | Where | Consequence |
|---|---|---|---|
| 1 | **Duplicate `id="editTitle"`** on the modal `<h2>` and the title `<input>` | `ui.ts:387,394` | `getElementById('editTitle')` returned the `<h2>`, so `el('editTitle').value = …` wrote a `value` property onto an `<h2>` and left the input blank. Editing a book's title silently did nothing. Renamed to `editBookModalTitle` / `editBookTitle`. |
| 2 | **`id="dashboardContent"` dropped by my own `<main>` edit** | `ui.ts` | The JS still toggled `dashboardContent`; after login the dashboard stayed `hidden` and the app looked broken. Retargeted to `main`. |
| 3 | **`[hidden]` was losing to author `display` rules** | `ui.css` reset | The UA stylesheet's `[hidden]{display:none}` is weaker than any class selector. This stylesheet sets `display` on `.container`, `.dashboard-grid`, `.settings-grid`, `.form-row`, `.pagination` and `.notice` — so toggling `hidden` on any of those did nothing. All six are JS-toggled. Fixed with `[hidden]{display:none!important}` in the reset. |
| 4 | **`.theme-toggle:focus-visible{outline-color:var(--accent-ink)}`** — a "fix" I wrote | `ui.css` | `--accent-ink` is `#ffffff` in light mode, and the toggle is transparent on `--ground` `#faf9f7`: a **1.04:1** focus ring, invisible on the one control I had specifically tried to make accessible. Rule deleted; the default ring already has contrast. |
| 5 | **Infinite `skeleton-shimmer` animation** left in the CSS | `ui.css` | Dead code that directly contradicts the MOTION-1 claim in `DESIGN.md`. Removed. |
| 6 | **`--border-strong` at 1.85:1** (light) / 1.53:1 (dark) | `ui.css` tokens | Every input and secondary-button boundary was below WCAG's 3:1 non-text floor. Darkened to `#8a837d` (3.62:1) / `#5f5956` (3.03:1). |
| 7 | **`--ink-faint` at 4.19:1 on row hover** (light) / 3.40:1 on surface (dark) | `ui.css` tokens | Placeholder and row-metadata text failed 4.5:1 in both themes. Now `#6b625c` (5.18:1) / `#948e89` (5.16:1). |
| 8 | **`confirm()` was unreachable** | `ui.js` | Native confirm dialogs are anchored to the page; the full-viewport `.overlay` sits above them, so the user could see the delete prompt and not be able to click it. Replaced with a two-step arm pattern styled by `.row-btn.armed`. |
| 9 | **Schedule-delete button had no accessible name** | `ui.js` | `.row-btn` is icon-only; `aria-label` was set, but the reading order meant the label named a time that had already changed. Refined to include the row context. |
| 10 | **The Edit button was completely dead — found only by clicking it** | `ui.js:557` | The single most serious defect found in this whole audit, and it survived a full read of the file. `openEditModal` looked up the book with `booksData.find(b => b.id === id)`. The id arrives from an inline `onclick="openEditModal('${id}')"`, so it is always a **string**; `book.id` comes off the JSON response and is always a **number**. `===` never matched, the function hit `if (!book) return;`, and it exited silently. Clicking Edit on any row did **nothing at all** — no modal, no error, nothing in the console. Every other field in that function was correct. Fixed by comparing as strings on both sides. Diagnosed only because R-35 forced a real click. |
| 11 | **The ISBN record plate broke across two lines** | `ui.css` `.plate` | An ISBN is a lookup key. It was rendering as `978-634-` / `97091-1-8` on two lines, which makes it uncopyable and defeats the record-plate motif `DESIGN.md` claims for it. Added `white-space: nowrap`; the cell is allowed to be as wide as the number needs. |

Note on defect 10: this was in the original code, not introduced by the fix pass.
It is listed because a report that only recounts the findings it was asked about
would have shipped a dead Edit button while claiming everything was verified.

   `settings.json` "is not in `.gitignore`." **That was wrong**; line 27 excludes
   it. I have now confirmed the tracking status with real commands rather than
   inferring it:

   ```
   git ls-files settings.json     -> empty. never committed
   git log --all -- settings.json .env -> none. never in any branch
   git log --all -S "<token value>"  -> none. the token string is in no commit
   git grep "<token value>" HEAD  -> absent from the working tree at HEAD
   ```

   I have substituted the token's own value for a placeholder in these commands.
   Writing the real one into a report is how a credential ends up in git history,
   and this repository has a GitHub remote. Run the commands with the real value
   substituted in your own shell; the result is the same.

   There **is** a remote (`git@github-nk:noorkhafidzin/isbn-notify.git`), so
   "it never left your machine" was not safe to assume. It turns out to be true
   anyway, because the file was never committed in the first place. **No rotation
   is needed.** The `NTFY_AUTH_TOKEN` in `settings.json` on disk is still live and
   still needs keeping out of commits; the gitignore is doing that job correctly.
